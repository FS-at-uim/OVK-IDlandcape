# ADR 0015: Bereitstellung der Konfigurationsdateien über das in Cloudflare hinterlegte Ziel-Repository

- **Status**: Accepted
- **Kontext**: Wenn die Editoren (`vermarkter_editor.html`, `core_editor.html`) oder die Map (`index.html`/`app.js`) auf einem eigenen Entwicklungs-Repository (z. B. `FS-at-uim/OVK-IDlandcape`) geöffnet wurden, luden relative `fetch('config/...')`-Aufrufe die lokalen Konfigurationsdateien des eigenen Repositories statt der führenden Dateien aus dem im Cloudflare Worker hinterlegten Ziel-Repository (z. B. `BVDW-org/ovk-identifiersupport`). Beim Speichern schrieb der Cloudflare Worker jedoch in das `BVDW-org`-Repository.
- **Entscheidung**: Das im Cloudflare Worker konfigurierte GitHub-Repository (`GITHUB_OWNER`, `GITHUB_REPO`, `GITHUB_BRANCH`, `GITHUB_BASE_PATH`) ist die alleinige führende Quelle (Single Source of Truth) für `config/core.js`, `config/data_partners.js` sowie `config/vermarkter/*.js`. Der Cloudflare Worker (`docs/gatekeeper_worker.js`) liest diese Dateien über die GitHub Contents API direkt aus dem Ziel-Repository aus und liefert deren Inhalt und Pfad-Metadaten sowohl bei `POST /login` (für `vermarkter_editor.html` und `core_editor.html`) als auch über `GET /configs` (für `app.js`) an das Frontend aus. Die Editoren laden keine lokalen Konfigurationsdateien aus dem Hosting-Repository mehr.
- **Konsequenzen**: 
  - *Vorteile*: 100% Konsistenz zwischen Lesen und Speichern über Repository-Grenzen hinweg; sofortige Sichtbarkeit gespeicherter Änderungen ohne CDN-Verzögerung; Unterstützung privater Ziel-Repositories über das im Worker hinterlegte `GITHUB_TOKEN`.
  - *Nachteile*: Änderungen an `docs/gatekeeper_worker.js` müssen im Cloudflare Worker Dashboard per Copy & Paste ("Save and deploy") aktualisiert werden, damit der Live-Worker die neuen Felder ausliefert.
